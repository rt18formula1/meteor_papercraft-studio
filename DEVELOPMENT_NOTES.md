# Development notes

## Implemented baseline

1. Added local photo import, direct image URL import, silhouette preview, transparent PNG export, colored PDF export, and an A4 calibration bar.
2. Added a local `.meteorcraft` project file storing image references, selected image, manual masks, tolerance, target width, and extrusion depth.
3. Added a 120-million-pixel project budget, a 25 MB / timeout limit for URL imports, and pixel checks before remote images enter the photo set.
4. Unified manual outline coordinates to a top-origin system so clicked outlines, transparent PNGs, previews, and PDFs use the same region.
5. Added physical 100 mm calibration bars to silhouette and mesh PDFs and documented 100% print verification.
6. Added automatic-mask confidence scoring based on border consistency and foreground area; low-confidence automatic outlines request visual confirmation.
7. Added commercial-output gating: low-confidence automatic masks require explicit confirmation, while manually confirmed outlines can proceed.
8. Added explicit multi-file type filters and recursive folder import for PNG/JPEG/TIFF/HEIC/GIF sources.
9. Added centrality-aware foreground component selection to reduce keyboard, stand, finger, and reflection selection in the supplied sample photos.
10. Changed automatic outlines from a convex hull to angularly ordered boundary pixels with printable reduction, preserving practical concavities.
11. Added macOS 14+ on-device Vision `VNGenerateForegroundInstanceMaskRequest` as the first background-removal path, with color-distance fallback on macOS 13 or Vision failure.
12. Passed the Vision mask into Object Capture so the native baseline follows: isolate each view locally, solve camera scale/pose and fuse views into USDZ, then unfold the USDZ.
13. Added `F1-Sample.meteorcraft` for the supplied five Formula 1 model photos.
14. Inspection of `papercraft-template.pdf` showed that it was generated by the old single-photo silhouette button: two copies of one side image plus a wrap band, not a photogrammetry mesh net.
15. The main export button now routes projects with three or more photos to the multi-view 3D path, preventing accidental legacy silhouette output.

## Supplied sample validation

`Meteor PaperCraft Studio_Sample-Data` contains five 4032×3024 PNG photos of a Formula 1 model. The subject is visible from top, front, rear, and both sides, but the set includes a keyboard, display stand, fingers, reflections, and a dark textured background. It is useful for mask and silhouette testing, but five views are below the recommended count for reliable native Object Capture reconstruction. The intended workflow is to mask each view, inspect it, and add more evenly spaced background-controlled views when a full photogrammetry model is required.

## Local 3D-generation candidates

Meshy is a hosted product benchmark rather than a local dependency. Its public feature pages emphasize image-to-3D, watertight/manifold output, repair, low-poly controls, textures, and export; this is the quality bar the app must approach without using its API.

TripoSR is MIT-licensed and supports local image-to-mesh inference. Its reference workflow needs about 6 GB VRAM for a single image and is primarily a single-image model, so it is a possible local fallback but not a complete multi-view solution.

MLX-MASt3R is Apache-2.0 and targets Apple Silicon with MLX. Its documented multi-view pipeline uses 3+ images, pair construction, camera pose/focal optimization, dense 3D points, confidence maps, and TSDF post-processing. It is the strongest architectural candidate for true local multi-view reconstruction on Apple Silicon, but it is a Python/MLX runtime rather than a tiny Swift library and requires model weights.

Modly is MIT-licensed and demonstrates a local desktop image-to-3D workflow with extension points, mesh smoothing/decimation, and Apple Silicon support. It is useful as a product architecture reference, but copying its application code would be a much larger migration than integrating a focused reconstruction runner.

## Local MLX backend

RealityKit Object Capture is not equivalent to Meshy, so it remains only the native baseline. The first focused local backend slice is now present: `scripts/local_multiview_reconstruct.py` runs MLX-MASt3R multi-view alignment, confidence filtering, and optional Open3D Poisson surface reconstruction. It rejects non-watertight meshes instead of sending them to unfolding. The Swift app exposes `ローカルAIで3D…`, invokes the bundled runner from the local virtual environment, and sends the repaired OBJ to the existing mesh exporter.

This backend still needs Mac hardware validation, model-weight download, and further mesh/texture quality work before it can be called commercial-ready. No hosted inference API is used.

The reconstruction runner now performs a papercraft-oriented post-process: Poisson output is cleaned, reduced toward a configurable 1,800-triangle target, and rejected if simplification opens the surface or creates non-manifold geometry. This keeps overly dense scan meshes away from the current unfolding limit.

The CAD direction is now explicit. `scripts/cad_profile_loft.py` uses CadQuery/OpenCascade to turn ordered millimetre cross-sections into a validated B-Rep loft and STEP/STL output. The image/ML stage must provide measured sections and constraints; the CAD kernel is responsible for topology, validity, and exact dimensions. This avoids claiming that an arbitrary photogrammetry mesh is equivalent to an Autodesk-style editable solid.

The CAD layer is now generic rather than Spark-specific: `scripts/cad_parametric_builder.py` accepts boxes, cylinders, loft sections, and fuse/cut/compound operations from a millimetre recipe. The F1 script remains a calibration fixture, while arbitrary objects can use the same feature graph after image/ML measurement and user correction.

The supplied screenshots showed an older app build: the old subtitle, missing folder/local-AI buttons, an empty photo list despite a count of five, and Object Capture error 6 being surfaced directly. The latest source now makes the list rows explicit in the scroll view and automatically falls back from failed Object Capture to the local AI route for three or more photos. The app must be rebuilt with `scripts/build-app.sh` on macOS to show these changes.

The latest screenshot confirmed that MLX-MASt3R completes alignment, but Open3D fails because Homebrew `libusb` was outside the app. The distributable build now copies the local Python environment into `Contents/Resources/local3d/.venv`, copies libusb into `Contents/Frameworks`, rewrites Open3D's dylib dependency to an app-relative rpath, and makes the app prefer the bundled interpreter. Customers therefore do not need a terminal, Homebrew, or a separate Python setup. Model weights are still downloaded on first use and cached under Application Support; this is the only first-run network step and is not an inference API.
